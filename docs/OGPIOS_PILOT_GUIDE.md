# OG-PIOS Pilot Demonstration Guide

> **⚠️ PILOT / SYNTHETIC DATA — NOT REAL OPERATIONAL DATA**
> Every well, facility, production number, equipment reading, maintenance record, cost, alert,
> and AI insight in this environment is synthetically generated by
> `backend/app/db/seed_wells.py`. Nothing in this environment represents a real company, a real
> field, or real production/financial figures. The application is not connected to any real
> SCADA/DCS/historian/ERP system. This is reflected in the UI itself: every screen carries a
> **"PILOT · SYNTHETIC DATA"** badge in the sidebar and on the login page.

## 1. Pilot objective

To demonstrate the complete OG-PIOS decision-support workflow — from a raw production anomaly
through equipment, maintenance, downtime, financial impact, alerting, AI-assisted interpretation,
what-if recovery modeling, and management reporting — end to end, using a coherent, relationally
consistent synthetic dataset, so a production manager can evaluate the platform's value without
needing any real field data connected.

This guide is a **demonstration aid**, not a training manual or a certification of production
readiness for any specific operator's environment. See [Important limitations](#6-important-limitations)
below.

## 2. The synthetic field

Seeded by `docker compose exec backend python -m app.db.seed_wells` (idempotent — skips if data
already exists) or regenerated by the reset tool (see [§5](#5-resetting-the-pilot-dataset)).
`random.seed(42)` is fixed at the top of the seed script, so **every fresh seed produces the
exact same dataset** — same wells, same equipment, same anomalies — making the demo repeatable.

| Entity | Count |
|---|---|
| Fields | 3 (Niger Delta Field, Permian Basin Field, North Sea Field) |
| Facilities | 6 |
| Wells | 25 |
| Production records | 9,150 (365 days × 25 wells) |
| Equipment items | 24, each with ~90 days of sensor readings |
| Maintenance records | 57 (routine, corrective, and emergency work orders) |
| Downtime events | 15 |
| Production-loss records | 10, each computed from a real downtime/decline event |
| Operating cost records | 264, across 11 cost categories (NGN for the Niger Delta field, USD elsewhere) |
| Commodity price points | 26 |
| Alerts | ~72 (generated by the real alert rule engine, not hand-written) |
| AI Insights | ~76 (generated by the real insight engine; deterministic rule-based fallback — see [§6](#6-important-limitations)) |

The dataset intentionally includes a mix, not a uniform "everything is fine" or "everything is
broken" set:
- **Normal wells** — the majority of the 25 wells, producing within their historical range.
- **High-performing and underperforming wells** — spread across all three fields.
- **3 wells with a genuine sustained production decline** (randomly selected by the seed, but
  fixed by the seed's seed value): `NSF-05-002`, `NSF-05-007`, `PBF-03-013`.
- **Healthy equipment** (most of the fleet) alongside **5 equipment items with a real, computed
  health issue**, including one in `failed` status with an open corrective/emergency maintenance
  trail.
- **Normal production periods and real loss events** — every `ProductionLoss` row is computed by
  the same calculation service the app uses for real data (`production_loss_calculations.py`),
  from an underlying downtime or decline event, never a disconnected random number.

Every record is relationally valid by construction: every production/pressure/temperature record
references a real well, every equipment item references a valid well or facility, every
maintenance/downtime/loss record references real equipment or a real well, and every alert/AI
insight references the real entity that triggered it.

## 3. The demonstration scenario: Well NSF-05-002

This is a **real** scenario present in the current dataset, not a scripted example — it was
selected because it is the richest, most naturally-occurring chain in the synthetic field, and
because nothing in the write path (there is no manual "create alert" or "create insight"
endpoint) was used to force it. Every alert and insight below is exactly what the app's own rule
and insight engines produced from the raw synthetic production/downtime data.

**Well NSF-05-002** — North Sea Field, NSF Platform A, gas-lift artificial lift, status `active`.

- **Production**: Oil rate held a steady ~490–535 BOPD for most of the last 30 days, then dropped
  sharply over the final ~2 weeks to **283 BOPD** as of the most recent record — a clear,
  sustained decline, not day-to-day noise.
- **Equipment**: Its gas-lift unit (`gas_lift-NSF-05-002`) has a **healthy** computed score
  (97.7/100) — the decline is *not* explained by equipment deterioration here, and OG-PIOS does
  not force one onto it. (See [§3.1](#31-a-second-equipment-example) for a genuine equipment
  deterioration case elsewhere in the field.)
- **Maintenance**: One completed routine work order (`WO-000001`, $4,541).
- **Downtime**: Three events — a flowline leak (Dec 2025), a reservoir shut-in (Apr 2026), and a
  **scheduled workover that began Aug 8, 2026 and is still open** — the most recent and most
  likely operational driver of the current decline.
- **Financial impact**: Two production-loss records tie directly to real events —
  $31,618.80 (≈408 bbl) linked to the ongoing workover, and $14,486.37 (≈218 bbl) linked to the
  flowline leak.
- **Alerts** (5, all real, all generated by `run_alert_rules`): Production Below Target
  (critical), Production Decline (high), Production Outage (critical), High Production Loss
  (critical), High Estimated Lost Revenue (high).
- **AI Insights** (5, all real, all generated by `run_insight_engine`): the same set of
  observations restated with possible contributors and a recommended investigation — each
  carrying the mandatory `disclaimer_text` framing it as an estimate requiring engineering
  review, never a guaranteed conclusion (see [§6](#6-important-limitations)).

**The natural read**: production dropped in step with an ongoing workover — a plausible,
investigate-worthy correlation, not a certainty. That is exactly the kind of "possible
contributor, not a guaranteed conclusion" framing OG-PIOS is designed to surface.

### 3.1 A second equipment example

To show genuine equipment-driven deterioration (deliberately *not* forced onto the same well as
the production-decline story), point to **`rod_pump-NSF-05-014`** on well `NSF-05-014`:
status `failed`, computed health score **50.7/100**, one completed corrective work order
($9,498.25) and one emergency work order currently `in_progress` ($19,513.95), with an open
"equipment failure" downtime event. This is an independent, unrelated well — proof the dataset's
issues aren't artificially concentrated onto a single "demo well."

## 4. Pilot demonstration checklist (10–20 minutes)

1. **Dashboard** — Log in and land on the executive dashboard. Note the fleet-wide KPIs
   (oil/gas/water rates, producing well count) and the **PILOT · SYNTHETIC DATA** badge in the
   sidebar.
2. **Select field** — Navigate to Wells and filter/sort to North Sea Field, NSF Platform A.
3. **Review wells** — Open the wells list; note the mix of active wells and their current status.
4. **Identify production decline** — Open well **NSF-05-002**; show its production trend chart —
   the drop from ~500 BOPD to 283 BOPD is visible without any explanation needed yet.
5. **Investigate equipment** — From the well's equipment tab, show the gas-lift unit's healthy
   score. Optionally pivot to Equipment → `rod_pump-NSF-05-014` to show what a genuine equipment
   health issue looks like elsewhere in the fleet.
6. **Review maintenance** — Show the well's one completed routine work order — nothing recent or
   unusual here, reinforcing that maintenance isn't the driver either.
7. **Examine downtime/production loss** — Show the three downtime events, especially the
   **open scheduled workover starting Aug 8, 2026** — this is the strongest lead.
8. **Review financial impact** — Open Cost & Revenue / Production Loss for this well; show the
   two real dollar-figure loss records ($31,618.80 and $14,486.37).
9. **Review alerts** — Open Alerts, filter to this well; show the 5 real alerts (Production
   Decline, Production Below Target, Production Outage, High Production Loss, High Estimated
   Lost Revenue).
10. **Examine AI Insight** — Open AI Insights for the same well; show how the insight restates
    the same evidence with a recommended investigation and the mandatory disclaimer.
11. **Run a What-If scenario** — In the What-If Simulator, build a recovery scenario against this
    well's baseline (e.g. `production_loss_reduction_pct` = 100, or `downtime_change_pct` = -50 to
    model the workover finishing sooner); show the projected recovered production/revenue.
12. **Generate a management report** — In Reports, generate a `monthly_management` report scoped
    to North Sea Field; show the well and its financial impact rolled into the executive summary.
13. **Show Administration / audit trail** — As an Administrator, open Administration → Audit Log;
    show that user actions (including this demo session's own logins/navigation) are recorded,
    and System Health/AI Config, which shows the AI provider's real configuration state.

## 5. Resetting the pilot dataset

A CLI-only reset tool regenerates the same deterministic dataset described above from a clean
state:

```
docker compose exec backend python -m app.db.reset_pilot_data --yes
```

- Running it **without** `--yes` only prints what it would do — it never deletes anything.
- Wipes exactly the 22 synthetic *operational* tables (wells, production, equipment, maintenance,
  downtime, production loss, costs, alerts, AI insights, saved What-If scenarios, saved reports)
  and regenerates them via the same `seed_wells()` function the initial setup uses.
- **Never touches** `users`, `roles`, `system_settings`, or the `audit_logs` table — resetting
  demo data should never erase who has access or the record of what they did.
- **Refuses to run** if `ENVIRONMENT=production` is set, so it can never be pointed at a real
  deployment by mistake.
- Requires the same access level as the existing `seed`/`seed_wells` scripts (`docker compose
  exec`) — there is no web-exposed endpoint for this action.

Because of the fixed random seed, resetting always reproduces the same NSF-05-002 story described
in [§3](#3-the-demonstration-scenario-well-nsf-05-002) — the demo does not need to be re-scripted
after a reset.

## 6. Important limitations

- **This is a decision-support tool, not a control system.** It never operates valves, chokes,
  DCS/SCADA setpoints, pumps, or compressors, and never will.
- **AI Insights run without a configured LLM provider in this pilot environment.** `AI Config`
  (Administration) shows `provider: none`, `is_configured: false`. Every insight shown is
  produced by the real, deterministic rule-based engine — the same engine that runs when an LLM
  provider *is* configured — not a stub or hand-written example. If a real provider is
  configured, insights additionally get a natural-language interpretation layered on top of the
  same underlying evidence; the underlying findings do not change.
- **Every AI/analytics output carries a disclaimer** ("possible contributor," "estimated impact,"
  "requires investigation") and must never be read as a guaranteed conclusion — this is enforced
  in the data model itself (`AIRecommendation.disclaimer_text`), not just in this guide.
- **The synthetic dataset is randomly generated, not hand-authored to reach any particular
  conclusion.** The demo scenario in §3 was *found* in the generated data, not written into it —
  a different reseed with a different random seed would very likely surface a different well as
  the primary example.
- **No production data, real credentials, or real API keys exist in this environment.** All
  secrets are placeholder/development values in environment configuration (`backend/.env`),
  never committed to source control.
- **Known product limitations** (not specific to the pilot) are tracked in the root `README.md`'s
  Known Limitations section — review before presenting to a technical audience.

## 7. Troubleshooting

| Symptom | Likely cause / fix |
|---|---|
| Login page won't load / `ERR_CONNECTION_REFUSED` | Backend/DB containers aren't running. Run `docker compose up -d --build` from the repo root, wait for `db` to report healthy, then reload. |
| Dashboard/module pages show no data | Database hasn't been seeded. Run `docker compose exec backend alembic upgrade head` then `docker compose exec backend python -m app.db.seed_wells`. |
| Login fails with correct-looking credentials | Confirm you're using a real seeded account (`docker compose exec backend python -c "from app.core.database import SessionLocal; from app.models.user import User; db=SessionLocal(); [print(u.email) for u in db.query(User).all()]"`), and that you haven't tripped the login rate limit (10 attempts / 5 minutes per account) — wait 5 minutes or contact an Administrator to reset. |
| The demo scenario (NSF-05-002) looks different from this guide | The dataset was reset with a different seed script version, or reseeded manually with the module-level `random.seed(42)` removed/changed. Re-run the reset tool (§5) against an unmodified `seed_wells.py`. |
| AI Insights all show "rule_based" with no natural-language text | Expected in this pilot environment — no LLM provider is configured (see §6). This is a graceful fallback, not an error. |
| Reset tool refuses to run | It refuses whenever `ENVIRONMENT=production` is set, by design — this tool must never run against a real deployment. Confirm you're targeting the intended pilot/demo environment. |
